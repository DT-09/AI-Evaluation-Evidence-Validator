The acceptance problem

A supplier's score is not your acceptance decision.

Vendor demonstrations and broad benchmark scores rarely answer the buyer's exact operational question: does this workflow meet our criteria, on our cases, under the conditions we approve?

01 / Evidence

Proof is scattered

Test outputs, reviewer notes, criteria and version details can live in separate files and conversations. Reconstructing the decision becomes its own task.

02 / Consistency

Criteria can drift

Different suppliers or releases may be judged against different examples, thresholds or informal expectations. Comparison loses its footing.

03 / Change

Regressions need context

A new run may improve one measure and weaken another. Teams need to see the affected cases and the rule behind each status.

A controlled review process

From acceptance criteria to an evidence package.

The workbench evaluates structured outputs supplied by the buyer or its technical team. It records what the supplied evidence supports—and where it does not.

Define

Set a versioned protocol: workflow, criteria, severity, thresholds and hard-fail rules.

Supply

Provide the approved case set, candidate run export and any required human-review decisions.

Evaluate

Apply explicit checks and reviewer decisions. Inspect criterion summaries and case-level outcomes.

Preserve

Export a portable JSON evidence package and readable HTML report, with source hashes and limitations.

The supplier or buyer's technical team runs the AI system in its own environment. This workbench evaluates the resulting structured export; it does not connect to or execute the live system.

Scope, stated plainly

Useful by design. Honest about its boundaries.

A narrow scope makes the first assessment deliverable and its conclusions interpretable. Anything outside the supplied evidence remains outside the decision.

What it supports today

  • Local-first, single-user evaluation workflow.
  • Structured CSV inputs and a buyer-editable JSON acceptance protocol.
  • Explicit deterministic checks and separately supplied human-review decisions.
  • Case-level outcomes, thresholds, hard gates and baseline comparisons.
  • Portable JSON and HTML evidence exports with source-file hashes.

What it does not claim

  • No live vendor execution, production integrations or API connectors.
  • No production monitoring, drift detection or live-system telemetry.
  • No proof that the supplied cases represent every real-world condition.
  • No general semantic correctness, safety, security, fairness or compliance certification.
  • No hosted multi-user audit service or customer-validated performance claim.
Methodology

Make the rule visible before the result.

Acceptance is only as meaningful as its criteria, evidence coverage and review process. The protocol makes those assumptions inspectable.

Initial workflow focus: customer-support ticket classification and routing. Other protocol families are roadmap candidates, not represented as validated deployments.

Exact match, allowed values, required field, regular-expression match and human-review criteria. Each rule is attached to a protocol version, severity and threshold.
PASS means the supplied run met the stated protocol and evidence-coverage rules. FAIL means an explicit rule was not met. INSUFFICIENT EVIDENCE means required cases, reviews or coverage are incomplete. None is a universal statement about the system.
When a compatible accepted baseline is supplied, the workbench compares case and criterion statuses and identifies regressions and resolved failures. A comparison is only meaningful when protocol and case-set versions are compatible.
Exports record source-file hashes, protocol and run metadata, decision rules, outcomes and limitations. Hashes help identify source-file changes; they do not prove that source data is truthful, complete or representative.
